# Plink development audit — September 19, 2026

## Scope and evidence

This audit traces the Android notification listener, live session controller, encrypted TCP transports, pairing UI, macOS native notification bridge, reply routing, and continuity handlers. It includes the connected Pixel 10 Pro XL running Android 17 and the local Mac build environment. The original repository was checked out at `93f61c3`.

Baseline verification passed after configuring OpenJDK 17, Android SDK 36, and the installed Xcode toolchain: Android debug/release compilation, lint and unit tests; 36 Swift tests; and strict local macOS app signing. Compilation and unit tests do not establish real cellular call, audio, or notification-center reply parity.

## Findings at baseline

The table records defects found in the original revision. The verification section below records which fixes have subsequently been exercised. Priority P1 means a security or major reliability defect; P2 means a narrower correctness defect.

| ID | Priority | Finding | Required correction |
| --- | --- | --- | --- |
| SEC-01 | P1 | Unauthenticated partial TCP clients block both live receivers indefinitely | Bound unauthenticated read time on accepted sockets, including an absolute frame deadline so trickle traffic cannot extend it forever. Keep accepting with bounded concurrency or evict a stalled client; close every failed client. Do not change frame size limits. |
| SEC-02 | P1 | Stopping/reconfiguring sockets does not revoke accepted connections or release ownership safely | Give one application-owned session controller sole ownership of listener and accepted sockets. On stop, mark generation revoked, close/shutdown owned sockets to unblock IO, suppress callbacks from revoked generation, and await loop exit before rebinding. Close each descriptor exactly once; avoid closing a descriptor after another thread can reuse it. |
| SEC-03 | P1 | Persisted session keys outlive volatile replay windows and send counters | Keep send and receive state scoped to the durable key/session and preserve it across process/controller recreation, with serialized atomic persistence before dispatch. Alternatively establish an authenticated fresh connection epoch/session key on every reconnect and bind every frame to it. Merely resetting the receive high-water mark when sequence falls is unsafe. |
| SEC-04 | P1 | Debug APK exposes trust replacement and authenticated commands to any local app | Remove exported debug authority or make receiver non-exported. Prefer an instrumentation-only test entrypoint. If cross-process debug automation is essential, require a signature permission and an explicit controlled test build; do not expose it to arbitrary installed apps. |
| SEC-05 | P1 | Android reply freshness uses the time accept began, not arrival time | Evaluate time after the complete frame is received, immediately before authentication/freshness validation. Inject a Clock/provider for deterministic tests rather than capturing Instant at receiveOnce invocation. |
| SEC-06 | P1 | Uncaught send and reply-action exceptions escape Android coroutine boundaries | Catch IO, validation, and action exceptions at each event boundary, include executor execution inside that boundary, and continue processing later events. Always propagate CancellationException. Surface a failed reply result; do not equate local TCP write with delivered message. |
| SEC-07 | P1 | Android activates trusted pairing before the user can compare both displays | Split key exchange/preview from trust activation. Send a pending response first so both screens can display the same authenticated transcript. Require explicit local comparison confirmation plus a key-authenticated peer confirmation before persisting trust or enabling forwarding/replies. Failed or cancelled pairing must leave no active trusted session. |
| SEC-08 | P1 | Replaced or non-replyable notifications leave old reply capabilities executable | Invalidate previous route and live action for the notification key before every posted update, including blank/non-replyable updates that mapper would skip. Keep registration/revocation/execution atomic enough that a revoked generation cannot dispatch. Update/remove matching Mac notification contexts so UI reflects current capability. |
| SEC-09 | P1 | Reply dispatch ignores notification action authentication requirements | Fail closed for authentication-required actions in remote relay until an explicit Android unlock/authentication flow exists. Preserve that policy with route state and recheck at execution; also require an eligible free-form RemoteInput and non-null actionIntent. |
| SEC-10 | P1 | Mac pairing attempts retain reusable offers and confirmations after confirmation/restart | Every explicit new attempt gets a fresh nonce and clears pending response/code. Bind confirmation to one active attempt with expiry and consume it on accept/reject. Ignore queued callbacks from old attempt generations. Fully stop pairing listener before binding secure listener on same port, and report actual bind readiness. |
| SEC-11 | P2 | Concurrent per-event sockets conflict with strict sequence ordering | Use a bounded replay bitmap/window that accepts previously unseen out-of-order sequences, integrated with durable session state. Alternatively serialize sends on one ordered connection; merely locking the increment does not order separate TCP connections. |
| SEC-12 | P1 | Continuity switches are cosmetic; disabling Messages/Calls does not revoke forwarding | Persist the existing switch choices in one shared feature settings store. Check them in notification capture and reply execution, and revoke relevant outstanding reply capabilities when disabled. Read preferences in UI rather than ephemeral state. |
| SEC-13 | P2 | Mac notification reply contexts disappear on restart while delivered notifications survive | Either securely persist bounded, session-bound, expiring contexts and reconcile delivered notifications, or withdraw delivered reply notifications on startup/session change. Do not silently leave actionable stale notifications. Consume route only after validation and handle transport failure explicitly; do not blindly retry sends without acknowledgment/idempotency. |
| SEC-14 | P1 | Android signed arithmetic produces a different numeric pairing code for half of transcripts | Fold bytes into Long using 0L and modulo 1_000_000L (or use UInt consistently), then format six digits. Add shared vectors that explicitly include digest prefixes with high bit set. |
| SEC-15 | P2 | Pairing transcript omits reply endpoint and accepts ambiguous field serialization | Bind both peer endpoints and all trust-bearing version/identity fields in one unambiguous length-prefixed or canonical structured transcript, validated consistently on both platforms. Because phone endpoint is already available before preview, include it in the exchanged preview transcript. At minimum reject separators/control characters and mismatched/unsupported versions until wire format is revised. |

## Call audio feasibility

The previous documentation categorically ruled out cellular audio on Mac through public APIs. That conclusion was too broad. Apple documents `IOBluetoothHandsFreeDevice.acceptCall()`, `transferAudioToComputer()`, and hands-free service/SCO callbacks. These APIs compile against the installed SDK. They provide a candidate Bluetooth HFP implementation with the Mac acting as the hands-free device and the Pixel as the audio gateway. The deprecated `IOBluetoothAddSCOAudioDevice` is not proof of functioning audio.

A successful HFP control connection proves call control only. An SCO connection proves a Bluetooth audio transport only. Completion still requires a controlled real call proving remote speech on the Mac and Mac microphone speech at the other endpoint, plus decline, hangup, mute, handback, reconnect and sleep/wake behavior. No private Apple Continuity identity, iMessage or iCloud relay is claimed.

Sources: [Apple hands-free device API](https://developer.apple.com/documentation/iobluetooth/iobluetoothhandsfreedevice), [audio transfer to Mac](https://developer.apple.com/documentation/iobluetooth/iobluetoothhandsfreedevice/transferaudiotocomputer()), [Android InCallService](https://developer.android.com/reference/android/telecom/InCallService).

## Verification and remaining acceptance

The first checkpoint addresses all fifteen baseline findings in code. Follow-up reviewers also found and corrected incorrect saved-peer selection, startup restore races, outbox revocation/retry defects, premature receiver readiness, stale notification controls, and Mac call-state and rollback defects. Source review and targeted regression tests cover these mechanisms; they do not establish every native OS integration.

The final clean gate passed 111 Android unit tests, debug/release assembly, Android lint with zero errors and 27 warnings, 31 XCTest cases and 51 Swift Testing cases, Swift builds, and strict ad-hoc Mac signing/package verification. Dependency/version/style warnings remain recorded. The latest emulator run passed seven synthetic platform checks, including keyed notification removal, actual Android filesystem replay persistence, and encrypted Android–Swift reply execution with acknowledgment. Exact binary hashes and logs are indexed in [checkpoint verification](evidence/2026-09-19/checkpoint-1-verification.json).

No acceptance metric is marked 100% merely because a build passes. Call audio, actual carrier/app recipient delivery, human comparison of pairing codes, native Notification Center interactions, background recovery, and full visual/animation accessibility review remain open. The Mac was locked during the latest native UI attempt. Android large-text review found truncated supporting guidance, recorded for the next correction. [Captures and their limits](evidence/2026-09-19/README.md) distinguish appearance from functional verification.

The user shares the Pixel with another task. No timeout or stay-awake setting was changed. The screen was found on after earlier instrumentation and turned off; the latest read reported OFF with brightness zero. Continuous screen-off state is not claimed. The test-only package and temporary port mappings are absent. Further captures and roundtrips use an isolated emulator. Task-owned scratch files remain inventoried until their tests and reference reviews finish, then are removed without touching another task's data.
