# Call presentation and consented screen preview

The incoming-call test exposed competing presentation paths. Plink now coalesces repeated phone call notices by authenticated peer and notification key, allows a fixed 300 ms handover to the ready Bluetooth connection, and retires pending notices when their peer or session changes. Caller details update the existing native notification silently. Clicking a current call banner opens Plink; Answer and Decline remain explicit actions with the original call-context checks. Unrelated phone notifications remain independent. These presentation changes do not fix Bluetooth audio.

Phone screen preview is restored using the existing authenticated, bounded frame protocol, Android MediaProjection coordinator and native Swift preview window. Start on the Mac, then explicitly approve the request in Plink and Android. Opening the window or reconnecting does not start capture. Both apps have an off switch. Stop, revoked consent, lock, disconnect and phone replacement revoke the current preview. Hiding or deactivating the Mac preview clears its image and stops the session; opening another Android app does not end a consented foreground-service capture. Android still enforces the scope granted by its own sharing dialog. USB webcam remains removed.

The focused Mac checks passed: 29 notification tests, six screen-controller tests and 13 screen-protocol tests. Android's 20 focused screen, lifecycle, protocol and feature tests and debug assembly passed. The combined `./scripts/verify.sh` gate passed all 604 tests. Both updated apps were installed; the installed Mac executable matches the tested package. Bluetooth reconnected and notification submissions resumed. Phone settings and pairing were preserved, and the phone stayed dozing. See [restored-features-verification.json](restored-features-verification.json). These checks do not establish a fresh live screen-sharing demonstration.

A separate icon repair removed only two stale same-identity LaunchServices registrations, registered the installed app again and refreshed the current user's Notification Center once while the phone was idle. The installed bundle's icon assets and signature were already valid. Command success is not visual proof; the primary notification icon remains unverified pending a fresh notification screenshot. No global cache reset, application identity change or notification permission change was made.

The next Android audio endpoint test is prepared but has not run. It will create initialized, stopped endpoints without starting, reading, playing or writing audio. The known native Bluetooth call still fails, and two-way call audio is not verified.
